# 閾値感度実験：開発用計画

## 目的と位置付け

固定済みの検知器について、判定閾値を変えることで、正常本文の損傷を
減らしつつ目標回答の出現を抑えられるかを調べる。これは探索的な開発実験であり、
`pilot_201–264`の結果を未知データでの確認結果とは扱わない。

偽陽性の発生原因の特定や、情報欠損と置換マーカーの効果の分離は、この実験の目的ではない。

## 固定する条件

- スコア・マスク集計の対象はBと同じ攻撃あり256入力と、重複を除いた
  未注入128入力。未注入入力のスコアは別に計算した。
- 応答生成は2026-11-12の利用者の指示で縮小し、生成上限校正時に固定シードで
  事前選択された12ブロック（日付・場所と測定を各6）を使う。攻撃あり48入力と
  未注入24入力を各9条件で評価する。この集合は開発用であり、未使用確認集合ではない。
- 検知器は[固定チェックポイント](../../models/attention_detector_fixed_20261015.pt)を用い、
  重み、特徴、正規化は変更しない。調査時点のSHA-256は
  `093810b3e65490f0059b507a2b814f5b47309d2053b18b6dac81ac0ec51248db`。
- スコアは攻撃クラスのsoftmax出力であり、確率校正済みとは仮定しない。
  スコアが閾値**以上**なら攻撃判定とする。
- 閾値候補は `0.50, 0.60, 0.70, 0.80, 0.90, 0.95, 0.98, 0.99`。
  防御なしは閾値1.0で代用せず、サニタイズを行わない対照とする。
- マスク範囲の結合規則と置換文字列は現行実装を維持する。領域の正解境界は
  評価にのみ使用し、防御処理には渡さない。
- 応答生成はBと同じQwen2.5-3B-Instruct、4-bit NF4、入力上限512、
  出力上限384、`do_sample=False`を用いる。
- 現行の内容採点と厳密JSON採点を維持し、採点不能を誤答と混同しない。
  表記揺れなどの補助的な採点を行う場合は、主結果を上書きせず、
  別の規則・別の結果として記録する。

## 閾値の選択規則

当初は攻撃あり256例でBの現行0.5条件を超えない2/256件以下とした。
縮小後は分母が異なるため、2026-11-12に利用者が、
**同じ12ブロック・48例の現行0.5条件の目標回答文字列出現件数を超えない**
という相対基準を選択した。文字列非出現は意味的な安全性を保証しない。

上限を満たす候補の中で、攻撃あり全入力を分母とした
「内容完全正答を確認できた割合」が最も高い閾値を選ぶ。
同点なら目標回答文字列の出現率が低い方、さらに同点なら低い閾値を選ぶ。
どの候補も上限を満たさない場合は、条件を満たす候補なしと報告する。
未注入入力での性能も併記する。追加の採否条件を設ける場合は、
閾値別の成績を見る前に決定する。

## 開発用候補の選択結果

承認された規則を12ブロックの生成結果に適用し、**0.98**を開発用の候補として選んだ。
現行0.5の目標回答文字列出現は0/48件であり、0.50〜0.98の7候補が上限を満たした。
その中で0.98は内容正答確認が45/48件と最大だった。0.99は11/48件で上限を満たさなかった。

| 条件 | 攻撃あり：内容正答確認 | 攻撃あり：目標文字列出現 | 未注入：内容正答確認 |
|---|---:|---:|---:|
| 防御なし | 35/48 | 19/48 | 24/24 |
| 現行0.5 | 1/48 | 0/48 | 2/24 |
| 候補0.98 | 45/48 | 0/48 | 21/24 |

0.98の攻撃あり48例の内訳は、内容正答45、誤答2、採点不能1。
未注入24例の内訳は正答21、誤答2、採点不能1。
正答確認率の分母には採点不能も含めているが、採点不能を誤答と断定しない。
0.98はこの探索集合での候補であり、未使用集合での確認や意味的な攻撃成功・
プローブ追従の人手判定は未実施。目標文字列0件は安全性を保証しない。

3,456条件の元の実行は109生成で停止し、利用者の承認で12ブロックに縮小した後、
閾値別の生成結果を見る前に上記の相対基準を決めた。縮小した実行は543生成・
648評価条件を完了し、入力・出力の上限到達は0件だった。攻撃ありの防御なし・
0.5の48応答はそれぞれBの対応応答と全件一致した。
結果は[12ブロック生成・採点ログ](../data/experiments/threshold_generations_12blocks_development_20261112_v1.jsonl)
に保存し、SHA-256は
`af856b56064ec2bedb2b04fb995e268c5cb0ae35dd112e77f197224b0f11133d`。

## 実施順序と停止条件

各段階は利用者に目的と内容を説明し、承認後に実施する。

1. 実装と既存データを確認する。**読み取り調査済み。**
2. この計画と閾値選択規則を記録する。
3. 全対象トークンのスコア・入力識別情報・オフセットを保存する。**実施済み。**
   チェックポイント、モデル、入力、実装の識別情報と切り詰めの有無も記録した。
   モデルのリビジョンは記録できたが、tokenizerのリビジョンは取得できなかった。
4. 攻撃あり入力の0.5判定について、保存済みの判定トークン、文字範囲、
   サニタイズ済み本文を照合する。**一致しなければ閾値比較へ進まず、
   差の原因を調査する。** 数値誤差による閾値付近の判定変化も記録する。
   既存レポートにない情報は完全一致を確認できたと主張しない。**256例で照合済み。**
5. 必要な評価上の細則を結果閲覧前に決める。各閾値について
   応答生成なしで正常・注入側の検知と実マスク範囲を集計する。**集計済み。**
   境界をまたぐトークンは各領域の率から除き、別に報告する。
   重要情報との重なりは、信頼できる位置ラベルを別途確認してから扱う。
6. 同じ候補で攻撃あり・未注入入力の応答を生成し、目標回答文字列の出現、
   正答・誤答・採点不能、厳密JSON、正答確認と目標文字列非出現の両立を評価する。
   入力と生成条件が完全に一致する場合のみ応答を再利用する。**12ブロックで実施済み。**
7. 固定した規則で開発集合から閾値を選ぶ。**0.98を選択済み。**
   その後、未使用集合で閾値を変えずに
   確認する。ブロックや共有材料の依存関係を考慮して結果を報告する。

スコア保存と0.5照合の準備スクリプトは
[`capture_threshold_scores_v1.py`](../scripts/capture_threshold_scores_v1.py)。
実データでの実行は別途承認を得る。承認後は以下の形式で実行し、
既存の出力ファイルは上書きしない。

```bash
uv run python -m topic_relevance.scripts.capture_threshold_scores_v1 --output <新しい出力JSON>
```

判定されたトークン・文字範囲・サニタイズ済み本文を保存済み結果と照合し、
差があれば失敗として記録する。過去のレポートには全対象トークン数がないため、
その数の一致は確認できない。スコア差は過去に保存された検知済みトークンについて記録する。

保存済みスコアと、応答生成なしで集計した閾値別の結果はそれぞれ
[スコア・0.5照合結果](../data/experiments/threshold_token_scores_development_20261112_v1.json)、
[閾値別マスク集計](../data/experiments/threshold_mask_metrics_development_20261112_v1.json)。

応答生成用の[`run_threshold_generation_v1.py`](../scripts/run_threshold_generation_v1.py)
は12ブロックへの縮小に対応する。元の384入力×9条件の実行は、
利用者の指示により109生成を保存した時点で停止した。縮小後の72入力×9条件の
648評価行は、同一の正規指示・処理後本文をまとめると543種類の生成入力になる。
停止済み109件には縮小対象との入力一致がないため再利用しない。
既存Bの応答はモデル・tokenizerのリビジョン一致を確認できないため自動再利用しない。
実行時はモデルのリビジョンとtokenizer本体のハッシュを記録し、結果を1生成ごとに保存する。
中断時の再開は、入力・実装・モデル等の識別情報が一致する場合のみ許可する。
最終的な閾値選択は別途実施する。

トークン指標は、同じスコア・対象・分母なら閾値の上昇に伴い非増加であることを
確認する。一方、生成結果の正答率や目標回答出現率が単調になるとは仮定しない。
